## Goal

Let a user upload a PDF, DOCX, TXT or MD file and have it parsed, chunked, embedded and indexed in Qdrant, with a visible processing status. Retrieval (`search_my_files`), deletion and the files UI come in later passes.

## Background

Implementation plan v1.3 (`docs/02_outputs/05_implementation_plan.md`), milestone M3, roadmap group `007-rag`. Pass 1 covers **TASK-017** (upload API and storage) and **TASK-018** (ingestion pipeline). TASK-019 (retrieval tool), TASK-037, TASK-020 (deletion) and TASK-021 (files UI) are not touched here. Functional spec FS-004, AI design doc 08 section 6, threat LLM-T12 (parsers) and LLM-T11 (huge files).

## Acceptance Criteria

**TASK-017 Upload API & storage**
- [x] All validation errors from functional spec FS-004 are covered by tests (`FILE_TOO_LARGE`, `FILE_TYPE_UNSUPPORTED`, `FILE_DUPLICATE`, `FILE_LIMIT_REACHED`, missing part → 422)
- [x] `POST /files` stores the file on the uploads volume, inserts the row and enqueues `ingest_file` in one transaction
- [x] `GET /files` and `GET /files/{id}` are owner-scoped (another user's file is a 404)

**TASK-018 Ingestion pipeline**
- [x] Re-running a job produces no duplicates (same Qdrant points, same counts)
- [x] A failed parse sets status `failed` with a readable reason
- [x] A transient failure is retried; the last attempt leaves the file `failed`, never stuck in `processing`
- [x] Every point carries `user_id`; embedding spend is recorded in `usage_daily`
