# Scratch: 007-rag (TASK-017, TASK-018)

## Plan

**TASK-017 first (the job it enqueues is what TASK-018 handles).**

1. Migration `0002`: `files.status` default `pending` + CHECK `status IN ('pending','processing','ready','failed')` (existing `uploaded` rows, if any, become `pending`); `page_count` / `chunk_count` become nullable without default (the spec says null until known). Update `db/models.py`.
2. Config: `UPLOADS_DIR` (default `./data/uploads`; `/data/uploads` in Compose), constants `MAX_UPLOAD_BYTES = 20 MiB`, `MAX_FILES_PER_USER = 50`. Compose: named volume `uploads` mounted in `api` and `worker`; Dockerfile creates `/data/uploads` owned by `nexus`.
3. `app/services/files.py` (sniffing + validation + storage; no HTTP types):
   - extension allow-list {pdf, docx, txt, md}; content sniff: PDF `%PDF-` in the first 1 KB, DOCX = zip whose central directory has `[Content_Types].xml` and `word/document.xml` (no decompression), TXT/MD = no NUL bytes and mostly printable in the first 8 KB. The sniffed family must match the extension, otherwise `FILE_TYPE_UNSUPPORTED`
   - size counted while reading in chunks (stop at 20 MiB + 1 byte): `FILE_TOO_LARGE`; `Content-Length` pre-check rejects honest oversize early
   - SHA-256 while reading; the file is written to `<uploads>/<user_id>/<file_id>.part`, then renamed; the disk name never contains user input
   - one transaction: lock the user row (`FOR UPDATE`) so the 50-file limit holds under concurrency; duplicate check (`FILE_DUPLICATE`, also on the unique-constraint race), limit check (`FILE_LIMIT_REACHED`), insert row, `enqueue("ingest_file", {file_id}, key=f"ingest:{file_id}:{sha256}", user_id, max_attempts=3)`. Any failure after the disk write removes the file
4. `db/repositories/files.py`: owner-scoped `create`, `get`, `count`, `get_by_sha`, `list_page` (keyset on `created_at DESC, id`), same cursor style as conversations.
5. `api/files.py` + schemas (`FileOut`, `FilePage`): `POST /files` 202, `GET /files`, `GET /files/{id}` (malformed id is 404). `DELETE` stays for TASK-020. `Idempotency-Key` is accepted but not honoured (SHA-256 dedupe stops double creation; same open decision as message sends). Register the router in `main.py`.
6. Spec: list `FILE_LIMIT_REACHED` (409) and the file error codes in the response descriptions; patch version bump; regenerate the frontend client only if `schema.ts` changes.
7. Tests (written first, each seen failing): unit for sniffing and validation; integration for the API against Postgres (happy path, each error, isolation, concurrency of the limit, disk cleanup on duplicate, job enqueued with the right key).

**TASK-018**

8. Dependencies: `pypdf`, `python-docx`, `python-multipart` (upload parsing), `qdrant-client`. `uv lock`.
9. `app/rag/parsers.py`: `parse(path, mime) -> ParsedDocument(pages, page_count)`; PDF per page (encrypted -> "File is password-protected"; average < 20 chars/page -> "No extractable text — scanned PDFs are not supported yet"), DOCX paragraphs and tables in document order (page `None`), TXT/MD UTF-8 with latin-1 fallback. Limits: 500 pages, 2M characters, DOCX total uncompressed size cap (zip bomb). Whitespace normalised, control characters stripped, headings kept. A `ParseError(reason)` carries the user-readable text.
10. `app/rag/chunker.py`: recursive splitter (paragraphs, lines, sentences, words), 800 tokens / 120 overlap with `o200k_base` (`app/llm/tokens.py`), per page for PDFs, stable `chunk_index`.
11. `app/rag/embedder.py` + factory: `build_embeddings_client` in `llm/factory.py` (`openai.AsyncOpenAI`, 30 s, 3 retries; fake mode returns a deterministic hashed bag-of-words 1536-d vector so similar texts are close). `Embedder.embed(texts)` batches of 64 and returns vectors plus token count. Price row `text-embedding-3-small` ($0.02 / 1M tokens).
12. `app/rag/index.py`: `QdrantIndex`: `ensure_collection()` (collection `documents_v1` with alias `documents`; vectors 1536 cosine; payload indexes `user_id` (tenant) and `file_id`), `upsert(file, chunks, vectors)` with point id `uuid5(file_id, chunk_index)` and payload `{user_id, file_id, filename, page, chunk_index, text}`, then delete the file's points with `chunk_index >= n`; `delete_file(user_id, file_id)` (used to clean up after a failure). Collection alias name from `QDRANT_COLLECTION` so tests use their own.
13. `ingest_file` handler (registered in `jobs/handlers.py`, 5 min timeout, 3 attempts): owner-scoped load (missing file -> return), status `processing`, parse and chunk in a thread, embed, record spend in `usage_daily` (`requests=0`), upsert, status `ready` with `chunk_count` / `page_count` only if the row still exists. `ParseError` -> `failed` with the reason, job completes (no retry). Other errors -> retried; on the last attempt: purge partial points, `failed` with "Processing failed. Please upload the file again.", then raise so the job is recorded as failed. `JobContext` gets `embedder` and `index` (lazily built, injectable in tests). Logs carry ids and counts, never text.
14. `app.migrate main()` also calls `ensure_collection()`; Compose `migrate` waits for Qdrant.
15. Tests: parsers (good files built in-test, malformed corpus: truncated PDF, encrypted PDF, empty PDF, DOCX zip bomb, DOCX that is not a zip, binary renamed `.txt`), chunker (sizes, overlap, page boundaries, determinism), embedder (batching, token count), index and handler against real Qdrant (idempotent re-run, tenant payload, failed parse, retry then final failure, file deleted mid-job).
16. Gates and docs: coverage gates for `backend/app/rag`; `CHANGELOG.md`; `memory/ai.md`, `memory/api.md`, `memory/_index.md`; `backend/AGENTS.md` structure; move task and scratch files to `tasks/done/` only when the whole `007-rag` group is finished, so they stay in `active/` with pass 1 ticked.

## Uncertainties

- Which HTTP status `FILE_LIMIT_REACHED` should use (the spec does not say): 409, since it conflicts with the current state, like `FILE_DUPLICATE`
- Parsing runs in a thread under the job timeout; a thread cannot be killed, so a pathological PDF that makes pypdf spin would keep a worker thread busy after the job times out. Page and character limits are checked incrementally to keep that unlikely; a subprocess sandbox is not built
- `qdrant-client` / `pypdf` / `python-docx` versions that resolve for Python 3.14 (check `uv lock`)
- Whether the Compose volume ownership works for the non-root `nexus` user (a named volume copies ownership from the image directory on first use)
- No live OpenAI embedding call can be made (no key); real behaviour of the embeddings call is covered by the SDK contract and a stubbed client only

## What Will Be Skipped

- File deletion and `delete_file_vectors` job (TASK-020); `DELETE /files/{id}` stays unimplemented
- Retrieval tool, citations, recent-files context (TASK-019); the files UI and attach button (TASK-021)
- Scanned PDFs (OCR), `.doc`, other formats
- `Idempotency-Key` storage; upload rate limit (not in the spec)
- Caddy body-size limit and a subprocess parser sandbox (noted as follow-ups)

## Risks

- Disk and DB can disagree if the process dies between the rename and the commit: an orphan file on the volume (harmless, no row points to it). A cleanup sweep is a later concern
- Qdrant outage during ingestion: the job retries with backoff and then marks the file `failed`; the user can upload again after deleting (deletion arrives with TASK-020, until then a failed file keeps its SHA-256 slot)
- Changing the collection layout later needs the `documents_v2` backfill described in doc 08; the alias makes the switch atomic
