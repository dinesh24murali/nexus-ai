# Memory: API

> Conventions and quirks of the Nexus AI HTTP API. Source of truth: `docs/02_outputs/04_api_spec.yaml`.

- Base path `/api/v1`; dev server `http://localhost:8000`
- Error envelope: `{"error": {"code": "UPPER_SNAKE", "message": "...", "details": {}, "request_id": "..."}}`
- Resources owned by another user → **404** (not 403) to prevent enumeration
- Cursor pagination: `?limit=1..100 (default 30)&cursor=<opaque>` → `{items, next_cursor}`; cursor encodes `created_at|id`
- `Idempotency-Key` header supported on `POST /files` and `POST /conversations/{id}/messages`
- Streaming endpoints (`POST …/messages`, `…/regenerate`, `…/runs/resume`) return SSE; payloads are the `StreamEvent` union; stream ends after `done`, `interrupt` or `error`
- One active run per conversation (run lease) → second send returns 409 `RUN_IN_PROGRESS`; a lease left by a crashed API is reaped within ~60 s and the assistant message gets `status=failed`, `finish_reason=server_restart`
- Client disconnect does not cancel a run; only `POST …/runs/cancel` does
- During a deploy, run-starting endpoints return 503 `SERVICE_RESTARTING` with `Retry-After`
- 429 carries `Retry-After`; codes `RATE_LIMITED`, `BUDGET_EXCEEDED` with `details.scope = user | global` (USD budgets reset 00:00 UTC)
- `POST /auth/register` takes `invite_code` (required when `REGISTRATION_MODE=invite`); bad codes → 403 `INVITE_INVALID` (one response for unknown/used/revoked/expired)
- No data export endpoint in v1 (FR-005 deferred)
- `DELETE /me` -> 202 (TASK-028): schedules the purge of everything the user owns (see `memory/auth.md` for the request side, `memory/ai.md` for the job); 400 `CONFIRMATION_MISMATCH` for a wrong `confirm_email`; the purge runs within minutes (the user was promised 24 h)
- Upload: multipart field `file`; 413 `FILE_TOO_LARGE` (> 20 MB), 415 `FILE_TYPE_UNSUPPORTED`, 409 `FILE_DUPLICATE`, 409 `FILE_LIMIT_REACHED` (50 files)
- Spec lints clean with Redocly (warnings only: no license, placeholder server URL, health probes without 4xx); spec version 1.1.0
- **Implementation facts (TASK-004/006, 2026-11-21):**
  - Every response carries `X-Request-ID` (`req_<16 hex>`); a client-supplied one is honoured only if it matches that shape. Error bodies carry the same id
  - Any malformed or invalid body is `422 VALIDATION_FAILED` with `details.fields[] = {loc, msg, type}`; submitted values are never echoed. (FastAPI's generic 400 for undecodable bodies is mapped to 422)
  - `PATCH /me`: fields are optional but **not nullable**; `{}` is a valid no-op that returns the user; `memory_enabled` is a strict boolean
  - `/readyz`: Postgres and Qdrant are required (503 if down); Langfuse is optional and only checked when keys are configured (`degraded`, still 200). `/healthz` is liveness only
  - 404/405 and unknown routes use the error envelope (`NOT_FOUND`, `METHOD_NOT_ALLOWED`)
  - Contract tests: `backend/tests/contract/` (schemathesis against the spec, deterministic; `CONTRACT_FUZZ=random` to explore). Exclusions: Allow-header check until `DELETE /me` exists (TASK-028); positive-data acceptance on `POST /me/password`
- **Conversations (TASK-008, 2026-11-21):**
  - List order is `updated_at DESC, id ASC` (keyset; cursor = base64url `updated_at|id`, matches index `ix_conversations_user_updated`). Rename deliberately does NOT bump `updated_at` (it means last activity). `?cursor=` empty = first page; a cursor the server did not issue → 400 `BAD_REQUEST`
  - Another user's id, an unknown id and a malformed id are all the same 404 (never 422/403). Every repository function takes `user_id`; `repositories/conversations.get` once forgot to filter on it — keep `tests/api/test_isolation.py` growing with each user-owned resource
  - Title: trimmed, 1–100 chars, no NUL (Postgres text cannot store it → 422 instead of a 500). `POST /conversations` body is optional but a JSON `null` body is 422
  - Delete cancels this process's active run for the conversation (and waits until it is saved), then removes messages (FK cascade) and LangGraph `checkpoints`/`checkpoint_blobs`/`checkpoint_writes` rows for the thread
  - Backend integration tests read `TEST_DATABASE_URL` (default port 5432; Compose Postgres on a dev machine with a local Postgres is on 5433)
- **Chat (TASK-011, 2026-11-21):**
  - `POST /conversations/{id}/messages` and `/regenerate` stream SSE: frames are `event: <type>`, `id: <seq>`, `data: <json>`, `: ping` every 15 s. Order today: `run_started`, then any of `token`, `tool_start` → `citation`* → `tool_end` (file search, TASK-019), then `usage`, `done`; a failed run ends with `error` instead (no `usage`). `done.finish_reason` is `tool_limit` when the turn used all 6 tool calls. The tools node also emits an internal `spend` event (query-embedding tokens); `RunService._on_custom` bills it to the run and never sends it. Text streamed before a tool call is not part of the answer (the stored text is what follows the last call). Stored on the assistant message: `tool_calls` (`{id, name, args, status, summary}`) and `citations` (the API `Citation` shape). `route_selected` does not exist yet (router, M7). The `interrupt` event and `runs/resume` exist since TASK-023 (below)
  - Pre-stream failures are normal JSON errors: 404 (unknown/other user's/malformed id), 409 `RUN_IN_PROGRESS`, 409 `REGENERATE_NOT_SUPPORTED` (no final assistant answer to redo), 422 `content` (empty, whitespace-only, NUL, > 16000), 503 `SERVICE_RESTARTING` + `Retry-After: 10` while draining
  - The assistant message id is `uuid5(run_id, "assistant")`: the id promised in `run_started`, derivable by the reaper from `active_run_id`
  - Cancel = `POST …/runs/cancel` -> 202 always (idempotent; 404 only for a conversation that is not yours). The stream ends with `usage` + `done{finish_reason: cancelled}`; the partial text is saved with `status=cancelled` and appended to the LangGraph thread, so the next turn sees it. A cancel with zero tokens saves an empty `cancelled` message and leaves the thread untouched
  - Regenerate forks the thread from the latest checkpoint whose next node is `agent`, and **replaces** the last assistant row whatever the outcome (the forked thread no longer contains the old answer)
  - Run end = one transaction: lease released, assistant message, `usage_daily` (USD, `requests+1`), and (completed turns only) `generate_title` job (key `title:{conversation_id}`, so once per conversation). A run that finds its lease gone writes nothing and emits `error` INTERNAL
  - `GET /conversations/{id}/messages`: newest first, keyset cursor on `created_at|id`, user messages have no `usage` key (the spec's `usage` is an object, never null). `feedback` is the caller's own rating (-1, 1 or null)
  - **`Idempotency-Key` on send is NOT honoured** (accepted and ignored; a retry during a run is 409). Open decision: honouring it needs storage or a spec change
  - NUL characters in `display_name`, email, `title` and message `content` are 422 (Postgres text cannot hold NUL). Schemathesis flags these as "schema-valid request rejected" because the spec has no pattern for it: documented exclusions in `tests/contract/test_api_contract.py`
  - Spec is at 1.3.5 (1.3.2: `listMessages` documents 422; 1.3.3: `sendMessage` 400 may be `MODERATION_FLAGGED`; 1.3.5: `resumeRun` description and 429); the frontend client was regenerated
- **Tool approval (TASK-023, 2026-11-21):**
  - A run that hits a `web_search` ends its stream with `interrupt` (payload = the spec's `PendingInterrupt`: `interrupt_id` `int_<12 hex>`, `tool`, `args`, `created_at`, `expires_at` = +24 h); no `usage`, no `done`, no assistant message yet. In ONE transaction the lease is released and `conversations.pending_interrupt` is set (and the spend so far is added to `usage_daily`, `requests=1` for a send); `GET /conversations/{id}` and the list report it, which is how the card survives a reload. An approval that expired is still reported (the card says so) until a new message clears it
  - `POST /conversations/{id}/runs/resume` `{interrupt_id, decision: approve|edit|reject, edited_args?: {query}}` -> SSE of the resumed run (`run_started` has `user_message_id: null`). Order: draining 503 -> rate limit + budgets (`_admit`, so 429 is possible) -> 404 -> 409 `RUN_IN_PROGRESS` -> 409 `NO_PENDING_INTERRUPT` (nothing pending, another id, expired) -> 422 `VALIDATION_FAILED` (edit without a 1-400 char `query`; the approval stays) -> one UPDATE that takes the lease and clears the approval (a double click resumes once). The approval is consumed before the graph runs: if the resumed run fails, the user asks again (the failed run's message says so; the thread is repaired on the next message)
  - The resumed run is not a message sent in `usage_daily` (`requests=0`) and writes the one assistant message (`tool_calls` and `citations` of the whole turn: the earlier run's come from graph state `tool_log` / `citations`); its `usage` covers the resumed run only, the paused run's tokens are in `usage_daily` but not on the message. Trace name `chat.resume`
  - A new message while an approval is pending abandons it (`pending_interrupt` cleared in the send transaction). Before every send, and when a run is cancelled, `_repair_thread` answers a tool call the thread left open (an abandoned approval, a crash, a stop between the model and its tools) with an error ToolMessage "did not run"; a regenerate that pauses deletes the old answer at park time
  - A paused run has no lease, so `cancel` does nothing for it: rejecting is the way to end it
- **Limits, moderation and usage (TASK-014, 2026-11-21):**
  - Order of checks on `POST …/messages`: draining (503) → per-user rate limit → daily budgets → moderation → run lease (404/409) → store. Regenerate does the first three but no moderation (no new text). Cancel is never limited. Every refusal happens before anything is written
  - Rate limit: 30 sends/regenerates per user per minute (`CHAT_RATE_LIMIT_PER_MIN`), fixed 60 s window in `rate_limits` (key `chat:{user_id}`), one atomic `INSERT … ON CONFLICT` increment then compare, so a parallel burst cannot exceed it; refused attempts count too. 429 `RATE_LIMITED` + `Retry-After` (seconds to the window end)
  - Budgets: `USER_DAILY_BUDGET_USD` (0.50) and `GLOBAL_DAILY_BUDGET_USD` (5.00), UTC day, from `usage_daily.cost_usd` (chat runs and background jobs). At exactly the budget a new run is blocked; a run that started under it is never cut off, so a day can end slightly over. 429 `BUDGET_EXCEEDED`, `details = {scope: user | global, resets_at}`, `Retry-After` = seconds to 00:00 UTC. If both are exceeded, `global` is reported
  - Moderation: `omni-moderation-latest`, 5 s per attempt + 1 retry, whole call capped at 11 s. Flagged → 400 `MODERATION_FLAGGED` (message not stored, no lease, text never echoed or logged; only category names are logged). Any failure, timeout, unreadable response or a missing API key → fail-open: the message goes through, `moderation_skipped` is logged (error type only) and the run's trace gets the tag `moderation:skipped`
  - `GET /me/usage` = today's (UTC) `spend_usd`, `budget_usd`, `tokens_used`, `messages`, `global_cap_reached`, `resets_at`. `messages` counts runs started by a send; a regenerate writes `requests=0`, so it is not a "message sent" (it still costs spend and counts toward the rate limit and budgets)
  - Spend alert: after a run is saved, once the global day's spend is ≥ 80 % of the cap a single `global_spend_alert` WARNING is logged per UTC day (deduped with a `rate_limits` row `spend_alert:<date>`). Nothing routes that log line to a channel yet (ops step, with the uptime check of TASK-034)
  - Fake mode: a message containing `[[moderation:flag]]` is flagged and `[[moderation:down]]` simulates an outage (`llm/fake.py::FakeModerationClient`)
- **Feedback (TASK-016, 2026-11-21):**
  - `PUT /messages/{messageId}/feedback` `{score: -1|1, comment?}` -> `{message_id, score, comment, created_at}`. One row per (message, user): a second PUT **replaces** the rating and the comment (no comment clears it) and moves `created_at` to the new time. There is no way to withdraw a rating (not in the spec); the UI therefore ignores a second press on the chosen thumb
  - Only the caller's own **assistant** messages can be rated: someone else's, a user message, an unknown id and a malformed id are all the same 404. `score` must be an integer: `"1"` and `true` are 422 (`true == 1` in Python, so `_not_a_bool` guards it); `comment` is optional, not nullable, <= 1000 chars, no NUL; a blank comment is stored as none
  - The rating is stored first, then mirrored to the answer's Langfuse trace as the score `user_feedback` (see `memory/ai.md`); a Langfuse outage or an answer without a trace (`messages.trace_id` is null) never fails the request. The comment is `mask`ed before it leaves the process
- **Files (TASK-017, 2026-11-21):**
  - `POST /files` -> 202 `FileObject` (`status=pending`), `GET /files` (newest first, keyset cursor `created_at|id`), `GET /files/{id}` (another user's, unknown and malformed ids are the same 404), `DELETE /files/{id}` -> 204 (TASK-020, below)
  - The handler reads the multipart body itself (`request.form()`), not through a `File(...)` parameter, so an honest oversize `Content-Length` (> limit + 1 MB) is refused before the body is received; Caddy also caps `/api` bodies at 22 MB. Without a Content-Length the size is counted while streaming to disk and stops at the limit
  - Check order: extension -> stream to `<uploads>/<user_id>/<file_id>.part` (size + SHA-256) -> 422 if empty -> content sniff must match the extension (PDF `%PDF-`, DOCX = zip directory with `[Content_Types].xml` + `word/document.xml`, text = no NUL and < 2 % control bytes; a PDF or zip named `.txt` is refused) -> rename -> ONE transaction: user row `FOR UPDATE`, duplicate (409 with `details.file_id`), limit (409), insert, enqueue `ingest_file` (key `ingest:{file_id}:{sha256}`, 3 attempts). Anything after the rename that fails removes the file
  - The user's file name is data: base name only, control characters removed, 255 chars; the disk name is the file id. `files.storage_path` is relative to `UPLOADS_DIR`
  - `page_count` / `chunk_count` are null until the file is `ready` (PDFs only for pages). A `failed` file keeps its SHA-256 slot until it is deleted
  - `Idempotency-Key` on upload is accepted and ignored (the SHA-256 duplicate check stops a retry from creating a second file, but the retry gets 409, not the first response)
  - **Delete (TASK-020, 2026-11-21):** `FileService.delete` runs ONE transaction: `SELECT … FOR UPDATE` the file row (absent or another user's -> 404) -> `ensure_collection` + `QdrantIndex.delete_file(user_id, file_id)` -> cancel the still-`queued` `ingest_file` job (`queue.cancel_queued`) -> delete the row; the disk file is unlinked AFTER the commit (best effort, logged, never fails the request). A Qdrant failure rolls everything back: 500, nothing half-deleted, retry works. Deleting a file that is being ingested is safe because the worker's `mark_ready` is an `UPDATE` of the locked row: it waits, finds 0 rows and removes the points it wrote (`ingest_file`); `tests/services/test_file_delete.py` orders the bad interleaving on purpose (mutation-checked: without the row lock it fails). A second delete is a 404. Deleting frees the SHA-256 slot and the per-user count. The spec already had `DELETE` (204/401/404/500), unchanged
  - Limits are settings: `MAX_UPLOAD_BYTES` (20 MiB), `MAX_FILES_PER_USER` (50), `UPLOADS_DIR` (`/data/uploads` volume in Compose, shared by api and worker)
- **Memories (TASK-027, 2026-11-22):**
  - `GET /memories` (newest first by `created_at`, keyset cursor `created_at|id`, `limit` 1..100 default 30; bad cursor 400, bad limit 422), `POST /memories` -> 201, `PATCH /memories/{id}`, `DELETE /memories/{id}` -> 204, `DELETE /memories` -> 204 (idempotent). Another user's id, an unknown id and an evicted one are the same 404; a malformed id is 422
  - Text goes through `memory.policy` like the extraction job's: instruction-like or sensitive text is `422 VALIDATION_FAILED` with a fixed `details.fields[].msg` (reason only; the text is never echoed or logged), a create within 0.9 similarity of the caller's own memory is `409 MEMORY_DUPLICATE` (another user's memory never counts), text is stored as one clean line, `source` is `manual`, category `fact`; the 200 cap evicts the least recently used after a create
  - Works while `memory_enabled` is off (the switch only stops learning and reading; `PATCH /me` is the switch). `services/memories.py::MemoryService` opens one store per call with a lazy embedder: list/delete need no embeddings key; create/edit embed the text and record the tokens in `usage_daily` (`requests=0`; a dozen tokens cost less than the six decimals the table keeps, so the dollar figure rounds to 0)
  - Contract tests cover all five operations; `positive_data_acceptance` is excluded for `GET /memories`, `POST /memories`, `PATCH /memories/{id}` because the policy refuses some texts the schema accepts (documented 422)
- **Routing and memory by chat (TASK-038 / TASK-039, 2026-11-22):**
  - Event order for a NEW message: `run_started`, `route_selected {intent, source: router|command|fallback, confidence|null}`, then the usual events (`memory_updated {action, content}` for a save or a confirmed forget), `usage`, `done`, or `interrupt` (a forget card). A resume and a regenerate send no `route_selected` (resume continues inside the pipeline that paused; the stored route is in the checkpoint). Ordinary chat messages have `source: router`; a router failure or doubt is `fallback`; a slash command is `command` (confidence null)
  - Slash commands are parsed by the API before the graph, only at the very start of the message (`graph/commands.py`; case-insensitive; `/pdfx` and `/etc/hosts` are plain text). `/help`, a malformed command (usage reply) and a command for a pipeline that is not built or is switched off are answered with a fixed text and **no `route_selected`**: no graph, no model, no checkpoint entry (the stored answer has `intent` null and `messages.route_source = 'command'`; usage shows 0 tokens and $0; it still counts as a message sent and gets a title). Today `/memory ...`, `/help`, `/pdf`, `/pdf last` and `/brief` do real work (documents: TASK-041); `/research` answers "not available yet" until TASK-043
  - `messages.intent` / `messages.route_source` (migration `0003`, both nullable, CHECK-constrained) are set on the assistant message, also after a resume; `Message.intent` in the API is the stored intent (null for old messages, `/help` and usage replies). **Regenerate is refused (409 `REGENERATE_NOT_SUPPORTED`)** unless the last answer is a `general_chat` one (`intent` null from before routing counts; `route_source = 'command'` with a null intent does not). Until TASK-040 the UI still shows the button on those answers
  - `ROUTER_DISABLED`, `INTENTS_DISABLED`, `MEMORY_WRITES_DISABLED`, `TOOLS_DISABLED` are read per run (60 s cache) when a run starts or resumes; a command for a switched-off intent gets "switched off right now"
  - `forget_memory` card: `PendingInterrupt {tool: "forget_memory", args: {candidates: [{memory_id, content}] (1-3, best first)}}` (also stored on the conversation: it survives a reload, expires after 24 h, a new message abandons it). Resume: `reject`, or `approve` with `edited_args.memory_id` (required when there are several candidates, optional with one; must be one of the offered ids). **Anything else is 422 `VALIDATION_FAILED` and the card stays** (`edit`, a missing id with several candidates, an id that was not offered: `details.fields[].loc` is `body.decision` or `body.edited_args.memory_id`). An expired or already-answered card is 409 `NO_PENDING_INTERRUPT` and nothing is deleted
  - `extract_memories` is not queued for a `manage_memory` turn (the user managed memory directly) nor for a static reply, nor for a document slash command (`/pdf`, `/brief`: a command, not something the user said about themselves; a router-chosen document request is still read)
- **Documents (TASK-041 pipeline, TASK-042 endpoints, 2026-11-22):**
  - `/pdf`, `/pdf last` and `/brief <topic>` (or a router-chosen `generate_document`) stream `run_started`, `route_selected`, then `document_created {document}` (a `DocumentObject`, `status: pending`) and a short answer, `usage`, `done`. `/brief` pauses first at a `web_search` approval card (`interrupt`, the usual `runs/resume` with approve / edit / reject; `document_created` comes on the resumed run). A request that cannot start (nothing to convert, the day limit of 10, the budget cannot cover the worst case of about $0.037, web search off) is an ordinary answer with no `document_created`, never an error status
  - `GET /conversations/{id}/messages` now fills `Message.documents` from the table (owner-scoped; `[]` for messages without one) and `Message.route_source` (spec 1.4.0). A document answer has `intent: generate_document` and cannot be regenerated (409)
  - A document is made by the worker: `pending` until `render_document` finishes, then `ready` (with `page_count`, `size_bytes`) or `failed` (`error` is a fixed reason). The row survives the conversation (`conversation_id` becomes null); `message_id` is not a foreign key. The endpoints are below
  - **The documents API (TASK-042, spec 1.4.1):** `GET /documents` (newest first, keyset cursor like files: `limit` 1..100 else 422, a bad cursor 400), `GET /documents/{id}`, `DELETE /documents/{id}` (204: the row first, then the PDF; a render still running finds no row and removes what it wrote), `GET /documents/{id}/download`. All owner-scoped through `current.id`; an unknown, malformed or another user's id is the same 404 for every operation (`DocumentsService.delete`, `pdf_for_download`; the handlers parse the id themselves so a malformed one is never a 422)
  - Download: 200 `application/pdf` with `Content-Disposition: attachment; filename="<ascii>"; filename*=UTF-8''<title>`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`. The ASCII name keeps only letters, digits, space, `.`, `-`, `_` (no `..`, at most 80 characters, `document` if nothing is left) so a model-written title cannot add a quote, a parameter or a line break. `409 DOCUMENT_NOT_READY` while `pending` and when `failed` (different messages); a `ready` row whose file is gone, or whose `storage_path` would leave `UPLOADS_DIR` (`storage.resolve`), is a 404, logged by id
  - One `DocumentsService` instance (built in `main.py`, `app.state.documents`) serves the graph's pipeline and the API; it holds only the session factory and the settings
- **Deep research (TASK-043, 2026-11-22):** `/research <question>` (or a router-chosen `deep_research`, `output: chat | pdf`) streams `run_started`, `route_selected`, `progress {stage: planning}` and ends with an `interrupt` whose `tool` is `research_plan` and `args` are `{topic, queries[3..6]}` (nothing is searched yet; the card is on the conversation as `pending_interrupt`, survives a reload, is abandoned by a new message, expires after 24 h). `POST …/runs/resume` with `approve` (the queries as shown), `reject`, or `edit` + `edited_args.queries` (1 to 6 queries of 1 to 400 characters, de-duplicated; anything else is a 422 and the approval stays pending). The resumed run streams `progress {searching, done, total}`, one `tool_start`/`tool_end` pair per search (`web_search`), `citation` events, the report as `token`s, `progress {writing}` (and `{rendering}` + `document_created` for a PDF), `usage`, `done`. **Only the approved queries are ever searched.** The stored message has `intent: deep_research`, `tool_calls` (the searches), `citations` (the sources the report cites), `documents` (the PDF, kind `research_report`) and cannot be regenerated. A run that cannot start (budget for the worst case of about $0.043, the daily document limit when a PDF is asked for, web search off or not configured, nothing to research) is an ordinary answer with no `interrupt`. `ProgressEvent` is in the spec since 1.2.
