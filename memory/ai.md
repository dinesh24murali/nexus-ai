- **Responses API everywhere, `store=false`.** GPT-6 tool calling needs it.
- **`store=false` + reasoning models: encrypted reasoning items ARE needed (verified 2026-11-21 from `langchain-openai` 1.8.5 source and OpenAI docs/forum; no live API probe, `OPENAI_API_KEY` was empty).** With `store=false` the server keeps no reasoning items, so a tool loop must send the model's reasoning item back with its function call, and only the encrypted form can be replayed. `langchain-openai` drops reasoning blocks that lack `encrypted_content` when `store=False` and does **not** add the `include` itself, so the factory sets `include=["reasoning.encrypted_content"]` for every role with effort ≠ `none`. The default `output_version` (`responses/v1`) keeps those blocks in `AIMessage.content` (a list of blocks, not a string), so they travel in graph state and the checkpoint (test: `tests/graph/test_checkpointer.py`). **Consequences:** read text with `message.text`, never `message.content`; never strip content blocks when trimming/summarising; **verified live 2026-11-21 (TASK-019, `gpt-6.1-terra` effort low, Responses API, `store=false`):** a real run `human → ai(tool call) → tool → ai` through the graph with `search_my_files` finished with no "function_call without its reasoning item" error, called the tool once and cited `[1]`; the reasoning blocks travelled in graph state. Only tested with one tool call per turn and a short history: **re-check with `web_search` and parallel calls, NOT done in M4 (no live call was made; `tasks/deferred.md` D12)**.
- Reasoning tokens bill as output and add latency.
- Do not use: `gpt-4.1*` (shut down 2027-01-14), `gpt-5`/`-mini`/`-nano` (2026-12-11), `gpt-5.1`, `gpt-5.4-nano` (2027-04-01).

## Orchestration Graph

- **Framework:** `LangGraph` 1.x
- **Topology (v1):** `load_context → (summarize?) → agent ⇄ [approval →] tools → agent → END`; max 6 tool calls/turn
- **Topology (v1.1, ADR-0010):** slash-command parser (no model) or `load_context ∥ route` → `dispatch` → {`general_chat` (= v1 agent), `manage_memory`, `generate_document`, `deep_research`}; confidence < `min_confidence` / error → `general_chat`; `/help` is fixed text; resume never re-routes; kill switches `ROUTER_DISABLED`, `INTENTS_DISABLED` (runtime flags). Schedules and `smalltalk_help` were cut in task 003b (schedules → PRD backlog)
- **Prompt layout (cache-friendly):** system → `<summary>` → history → late context message (memories, date) → newest user message. Built in `app/graph/prompting.py`; the summary and context messages are **human** messages wrapping data, so user-derived text never gains system authority. A test asserts the prefix (everything before the late context message) is byte-identical across consecutive turns and after a summary is written. Because the context message sits before the newest user message, a turn's cacheable prefix ends where the previous turn's context began: reuse is one turn behind by design
- **Implemented graph (TASK-010, tools since TASK-019):** `START → load_context → (history > 24k tokens ? summarize) → agent ⇄ tools → END`. The `tools` node exists only when a retriever is given (`build_graph(retriever=…)`); without one the graph is the old tool-less one. `load_context` resets `memories`, `citations`, `tool_calls_this_turn` and loads `recent_files` (injected lookup `services/files.py::recent_files_for`; `user_id` comes from the run config). `summarize` keeps the most recent ≤ 12k tokens starting on a human message (a turn is never split, so no orphan tool results; the newest user message is always kept) and folds the rest into `summary`; if the summariser fails, chat continues with the full history. **Deviation from doc 08 §3:** the agent sends the state history unmodified (no sliding 12k window): a window would change the prefix every turn between 12k and 24k tokens and defeat caching, so "history ≤ 12k" holds right after summarisation and grows to 24k before the next one. Token counts use tiktoken `o200k_base` (falls back to chars/4 if the encoding cannot be loaded; the Docker image bakes it in)
- **Streaming (TASK-011):** `RunService` iterates `graph.astream(stream_mode="messages")` and keeps only chunks from node `agent` (the summariser is tagged `nostream` as a second line of defence). A model that does not stream is sent as one `token`. Usage and cost come from `llm/usage.py::UsageCollector` attached to the run config: it sees EVERY model call of the run (summariser, fallback model) and prices each per model; a call that reports no model name is billed to the chat model (the fake model reports none)
- **Cancel / reaper and the thread:** cancel appends the partial answer with `aupdate_state(as_node="agent")` (only if there is text). The reaper does NOT touch the checkpoint (deviation from doc 08 §2.3, now corrected there): the text a crashed process had streamed is gone, and an empty AI message in the thread is worse than none; the next turn simply sees two user messages in a row (tested with a real SIGKILL)
- **Checkpointer / thread-id strategy:** `AsyncPostgresSaver` (psycopg 3), `thread_id = conversation_id`; summary lives only in graph state; regenerate forks from the checkpoint before the last answer
- **Tools and approval (TASK-022/023, 2026-11-21):** the graph is `load_context → (summarize?) → agent ⇄ [approval →] tools`. `approval` (`graph/nodes/approval.py`) calls `interrupt()` once per call that needs approval and fits under the cap (a call past the cap or with invalid arguments gets its error result and no card); the payload is `{interrupt_id: int_<12 hex>, tool, tool_call_id, args, created_at, expires_at (+24 h)}`; decisions go to state `approvals` and the `tools` node acts on them (approve runs, edit runs with the edited query and tells the model so in the ToolMessage, reject / no decision does not run: `tool_end` status `rejected`). Several interrupts in one node (two searches in one message) are answered one at a time in call order; nothing runs until the last is decided (verified). State also has `tool_log` (the turn's calls in the API `ToolCall` shape) so a resumed run can store the whole turn. `Command(resume=None)` crashes LangGraph and `{}` does not resume: the API always sends `{"decision": ...}`. The kill switch `TOOLS_DISABLED` is per run (`config["configurable"]["disabled_tools"]`): the agent binds only the tools that are on (models per subset are cached), approval and tools skip a disabled one. **Interrupt (HITL) points:** `TOOL_POLICY` — `web_search` every call (a message with mixed calls interrupts before any runs; all run after the decision); v1.1: `research_plan` once per research run (only approved queries run), `forget_memory` before every memory delete by chat (1 clear match or up to 3 candidates); pending interrupt mirrored to `conversations.pending_interrupt`, expires after 24 h
- **Tools in the graph builder:** `build_graph(retriever=, web_searcher=, calculator=)`; the `tools` node exists when any is given. Production (`graph_factory_for`) always has the calculator, file search when a retriever is configured and `web_search` when `TAVILY_API_KEY` is set (or in `LLM_MODE=fake`, with the offline `FakeWebSearcher`; with no key the tool is simply not offered). `build_web_searcher` is in `llm/factory.py`.
- **Tool cap (implemented, TASK-019):** 6 individual calls per turn (`state.MAX_TOOL_CALLS`); `tools` (`graph/nodes/tools.py`) runs a message's calls together (each under a 10 s timeout, searches in parallel, `[n]` numbers assigned afterwards in call order so numbering is deterministic), the calls past the cap get a `ToolMessage` "tool limit reached" (status error) and the agent's next call is made on the model **without tools** (not `tool_choice="none"`: factory models bind tools to primary+fallback, so the unbound model is the simple robust form; **verified live 2026-11-21**: the real model, given a history that contains a tool call, its reasoning item and the result but no tools bound, answered normally with no tool calls and no API error) — and the run ends with `finish_reason=tool_limit` whenever the count reached 6. Tool failures become error results for the model and never carry exception text (it can name internal hosts). Unknown tool names and invalid arguments get error `ToolMessage`s so every `tool_call_id` is answered. Events go out through the stream writer (`tool_start`, `citation`, `tool_end`, internal `spend`); `citations` live in graph state as a plain list (a reducer cannot reset it)
- **Run lease:** `active_run_id` + `run_heartbeat_at` (10 s); worker `reap_stale_runs` (30 s, stale after 60 s) writes a `failed` message (`finish_reason=server_restart`, empty content); graceful drain 90 s on SIGTERM (verified on the Compose stack: a stream open at SIGTERM finished and the container exited 0 in ~8 s; uvicorn runs with `--timeout-graceful-shutdown 105`)
- **Tenant context:** `user_id` comes from `config["configurable"]`, never from model/tool args

## Background Jobs (TASK-012)

- Postgres queue in `app/jobs/queue.py`: claim = `SELECT … FOR UPDATE SKIP LOCKED` (oldest `run_after` first); every later transition (`complete`/`fail`/`release`/`heartbeat`) is conditional on `locked_by`, so a worker whose job was requeued cannot finish someone else's run. Retry backoff 10 s, 20 s, 40 s … capped at 2 min; `enqueue` joins the caller's transaction and is idempotent on the key
- Worker (`app/worker.py`): 4 claim loops, 1 s poll, only claims kinds it has a handler for; per-job heartbeat refreshes `locked_at` every 30 s; hard per-kind timeout (`generate_title` 120 s, 2 attempts); a worker that finds it no longer holds its job cancels the handler and writes nothing; on SIGTERM it stops claiming, waits up to 100 s, then releases running jobs back to the queue with the attempt refunded (Compose grace is 120 s)
- Periodic (`jobs/periodic.py`, idempotent, safe in several workers): `reap_stale_runs` 30 s, `requeue_stale_jobs` 30 s (running job without a heartbeat for 2 min; one that used all its attempts fails instead), `cleanup_invites` daily (UNUSED invites expired/revoked > 30 days; used ones stay as the join record), `cleanup_rate_limits` daily (> 1 day old)
- Jobs call models only through the factory (`JobContext.model(role)`), are traced as `job.generate_title`, and record their spend in `usage_daily` with `requests=0`
- `ingest_file` (TASK-018): see Retrieval below; 300 s timeout, 3 attempts; spend recorded with `requests=0`
- `extract_memories` (TASK-025): see Long-term Memory below; 120 s timeout, 2 attempts, key `mem:{assistant_message_id}`, spend recorded with `requests=0`, traced as `job.extract_memories` (feature `memory`, hashed user id, **no** assistant message id: the chat run's trace is derived from it)
- Not built yet: `delete_file_vectors`, `purge_user`, `render_document`, `cleanup_documents`. The `jobs` table is never pruned (one `generate_title` row per conversation so far)
- Tests that wait for time are scaled (0.1 s heartbeat, 0.5 s stale window, 1.5 s job) because a real 5-minute job cannot run in a unit test; `test_without_a_heartbeat_the_same_job_would_run_twice` is the negative control proving that test can fail

## Retrieval

- **Vector DB:** `Qdrant` 1.x, collection alias `documents`, queried with `query_points`
- **Embedding model / dimensions:** `text-embedding-3-small`, 1536, cosine
- **Chunking:** 800 tokens / 120 overlap (`o200k_base`), never across PDF pages
- **Top-k / rerank:** search 8 (score ≥ 0.25) → dedupe → top 5, ≤ 3k tokens; no reranker in v1
- **Tenant isolation filter:** `user_id` payload (tenant index) added in retriever code
- **Ingestion (TASK-018, 2026-11-21):** `app/rag/{parsers,chunker,embedder,index}.py` + `ingest_file` in `jobs/handlers.py`. Parse in a thread (PDF per page with pypdf; DOCX paragraphs + tables in order, headings as `#`; TXT/MD UTF-8 then latin-1). Limits: 500 pages, 2M characters, DOCX 100 MiB unpacked (checked from the zip directory before anything is read), PDF average < 20 chars/page = "scanned PDF". A `ParseError` reason is stored in `files.error` and the job completes (no retry); other errors are retried and the last attempt marks the file `failed` ("Processing failed. Please upload the file again.") after deleting partial points. Embedding spend is written to `usage_daily` right after the embeddings return, before indexing
- **Qdrant layout:** collection `documents_v1` behind alias `documents` (`QDRANT_COLLECTION`), created by `python -m app.migrate` and lazily by the job; payload indexes `user_id` (`is_tenant`) and `file_id`; point id `uuid5(file_id, str(chunk_index))`; payload `{user_id, file_id, filename, page, chunk_index, text}`. A re-run overwrites and then deletes points with `chunk_index >= n`
- **Retrieval (TASK-019, 2026-11-21):** `app/rag/retriever.py::Retriever.search(user_id, query, file_ids)`: embed the query (spend is billed to the run: `UsageCollector.add_embedding`, cost only, not chat tokens), `QdrantIndex.search` with the `user_id` condition added INSIDE the index (a caller cannot leave it out; `file_ids` only narrows), `limit 8`, `score_threshold 0.25`, merge consecutive chunks of one file and page (joined with a blank line; the 120-token overlap is not removed), top 5 by score, ≤ 3000 tokens (a passage that does not fit is skipped, a lone oversize passage is kept). `graph/tools/search_my_files.py`: args `query` 1..400 and `file_ids` ≤ 10 (extra keys such as `user_id` are ignored), passages as `<document index file_id title page>` with the text and title HTML-escaped (a passage cannot close the tag or open another), snippets ≤ 300 chars, an empty result says so and cites nothing. Production builds the retriever lazily (`lazy_retriever`), so the API starts without an OpenAI key and a run fails like a chat run would. Tests: `tests/rag/test_retriever.py`, `tests/rag/test_isolation.py` (graph + tool + real Qdrant: user B gets nothing, even naming A's file id and passing A's `user_id`; mutation-checked once by removing the tenant filter), `tests/graph/test_tools.py` (4+3 parallel calls → 6 run, 7th refused, forced answer without tools)
- **Known limits:** a parser runs in a worker thread that cannot be killed, so a pathological file could keep a thread busy after the 300 s job timeout (page and character limits are checked while reading to make that unlikely; a subprocess sandbox is not built). `rag.golden` exists but has not been run on the real model yet (see Eval Status), so chunk size/overlap, the 0.25 threshold and top-5 are the doc 08 defaults, untuned. Whole-document questions rely on the top chunks (no synopsis / `get_file_overview`). **Synopsis decision (2026-11-21): not built, and NOT settled for long documents.** On the smoke run the model searched on 4/4 whole-document questions and 3 were fully correct, 1 vague (whole_doc correctness 0.875), so the pre-registered rule says "no synopsis". **But the evidence is invalid for the real question:** every fixture document is shorter than one chunk (800 tokens), so a search returns the WHOLE document and a whole-document question is trivially answerable from top-k. The synopsis matters for files with dozens of chunks, where top-5 covers a small part of the file; the corpus has none. Do not read this result as "top-k is enough". To decide: add one long fixture (about 40 chunks, e.g. a 30-page report) and 2-3 whole-document questions about it with key facts spread across the file, run smoke again, then apply the rule (searches and covers the facts → no synopsis; covers only part → per-file synopsis stored at ingestion by one background-model call, wrapped as data, returned with `file_ids` queries, in preference to a `get_file_overview` tool: no extra tool to choose, no routing risk). Until then the product behaviour is "whole-document questions see only the best-matching passages". The file-then-web multi-step cases still need `web_search` (TASK-022). **Live embeddings verified 2026-11-21:** `text-embedding-3-small` returned 1536-d vectors and `usage.total_tokens` (43 tokens for two short chunks), and the real `Embedder` + Qdrant + `Retriever` found the right chunk

## Tools (TASK-022, 2026-11-21)

- **`calculator`** (`graph/tools/calculator.py`): `ast.parse` + a whitelist walk, `Decimal` at 50 digits, results below 1e300, ≤ 200 chars, ≤ 120 nodes, depth ≤ 40, one line, 1 s timeout in a thread. Functions `sqrt`, `log` (natural, or `log(x, base)`, snapped to an integer when within 1e-42 so `log(1000, 10)` is `3`), `round` (half up), `abs`; `×`, `÷`, `−` are accepted, `^` is not (use `**`). A result that does not fit the precision or is irrational is prefixed "approximately"; `round` does not count as an approximation. Floats are taken from `repr`, so a decimal literal with more than ~17 digits loses the extra digits (integers are exact). `//` and `%` follow Python (floor), not Decimal (truncate). Safety tests: `tests/graph/test_calculator.py`
- **`web_search`** (`graph/tools/web_search.py`): `TavilySearcher` posts `{query, max_results: 5, search_depth: basic, include_answer/raw_content/images: false}` to `https://api.tavily.com/search` with `Authorization: Bearer <key>` (**from Tavily's public docs, never called live: no key was used and no query was sent**), 10 s timeout, ≤ 5 results × 800 chars, only `http(s)` URLs, domain without `www.`, results as `<web_result index url domain title>` blocks (attributes and text escaped) and web `Citation`s (`snippet` ≤ 300). The key is a `SecretStr`, absent from `repr`, errors and logs; failures become "The web search failed / timed out. Answer without it" results. Tavily credits are not tracked in `usage_daily`
- **Not built:** the 100 web searches per user per day limit, red-team records for the new tools (`tasks/deferred.md` D6, D13)

## Long-term Memory

- `AsyncPostgresStore`, namespace `("memories", user_id)`, embedding index on `content`
- Read: top 8 relevant + 5 recent preferences, ≤ 600 tokens, as `<user_memory>` data in the late context message
- Write: `extract_memories` job after each turn (≤ 3 ops; user message is the only source; skipped on `manage_memory` turns; `create` dropped at ≥ 0.9 similarity to an existing memory) and, from v1.1, `manage_memory` save/forget. No memory-writing tool in `general_chat` (`remember_fact` and its taint rule removed in task 003b); 200-item cap
- **Built (TASK-025, 2026-11-21): the write side only.** `app/memory/`: `store.py` (`MemoryStore` over `AsyncPostgresStore`, index `{dims: 1536, fields: [content], distance_type: cosine}`; every method takes `user_id` and builds the namespace `("memories", str(user_id))` itself, so another user's key is simply "not found"; `search` scores are cosine similarities, 1 = identical; value `{content, category, source, conversation_id, created_at, updated_at, last_used_at}`; **one store (one connection) per job**, because the store batches calls on its own task so a contextvar cannot carry the job's embedding-token count; `evict_to(user, 200)` deletes the oldest `last_used_at`, which is set at write time, **TASK-026 must refresh it when a memory is read into a prompt**), `policy.py` (pure: normalise, length 1..500, instruction-like text, sensitive deny-list by category: health, religion, sexuality, politics, location, credentials; accents/case/full-width folded; returns a reason code, never text), `extract.py` (`plan_ops` = prompt + `with_structured_output(MemoryOps, method="json_schema", strict=True)` + `filter_ops`: ≤ 3 ops, `update`/`delete` only for ids that were shown to the model (so another user's id, or an invented one, is dropped), one op per memory, create/update text through the policy; `apply_plan` = duplicate drop at ≥ 0.9 inside the user's own namespace, missing targets skipped, cap enforced). `python -m app.migrate` creates the store with the index (needs pgvector: `store_vectors`, `vector_migrations` are LangGraph-owned tables like the others)
- **Job rules:** queued in the run's own transaction for a completed `send` or `resume` (not `regenerate`) when `users.memory_enabled`; the job checks `memory_enabled`, account status and the `MEMORY_WRITES_DISABLED` flag again before any model call (either can change in between); it shows the model the 20 memories most similar to the user's message; spend (model + embeddings) is recorded in a `finally`, so a failed attempt is still billed to the user's budget. Memory text is never logged: the job logs counts and reason codes (`rejected: [sensitive:health, ...]`)
- **Known limits:** the filters are patterns, so paraphrases get through and some harmless text is dropped ("church organist"); a sentence that starts with a command word ("Never eats meat") is refused, the prompt asks for "User never eats meat"; the doc 08 model-based post-filter classifier is NOT built (deferred D16); nothing reads memories yet (TASK-026) and there is no API or UI (TASK-027)
- **Fake mode:** role `memory_extract` answers from the `<user_message>` block only: a `[[fixture:id]]` fixture's `memory_ops`, else "remember (that) X" becomes one `create` ("I prefer Go" -> "User prefers Go"), else no ops

## Known Failure Modes & Gotchas

- SSE needs unbuffered proxies (Caddy `flush_interval -1`, `X-Accel-Buffering: no`)
- Langfuse SDK v5 (5.2.0) default export filter keeps every span created by its own tracer, so LangGraph node spans from `langfuse.langchain.CallbackHandler` are exported; `llm/tracing.py` still states the filter explicitly (`should_export_span`) and a test asserts a node span (`agent`) and a generation both arrive. The client is a per-public-key singleton; metadata values are JSON-encoded once (pass dicts, not JSON strings); `propagate_attributes` limits (ASCII ids ≤ 200 chars, metadata values ≤ 200 chars) apply. Trace fields come from RunnableConfig metadata keys `langfuse_user_id`, `langfuse_session_id`, `langfuse_trace_name`; prompt name + version go in trace metadata `prompt_versions` (not Langfuse prompt linking, since prompts are not fetched from Langfuse)
- Tracing helpers: `app/llm/tracing.py` (`Tracer.run_config(RunTrace, mode="run"|"eval")`; eval mode attaches no per-node callbacks), `app/llm/redaction.py` (`mask` for emails, phones, Luhn-valid cards, IBANs, JWTs, API keys; `hash_user_id` = HMAC-SHA256 keyed with `APP_SECRET`, 32 hex chars), `app/llm/pricing.py` (Decimal; unknown models priced at the highest known rate so budgets never under-count), `scripts/sync_prompts.py` (fails when a prompt's text changed without a `version` bump)
- Alias-only GPT-6 models can change silently; the **weekly** full eval is the drift alarm (up to a week of lag)
- Eval runs send one trace per case (no per-node spans; `evals/langfuse_log.py`); the CI Langfuse project is in its own organisation (Hobby quota)
- **Trace id = function of the assistant message id** (`Tracer.trace_id_for` = `Langfuse.create_trace_id(seed=message_id)`, passed to the callback handler as `trace_context`; verified in `tests/llm/test_tracing.py` that every exported span carries it). `RunService` stores it in `messages.trace_id`, and a user rating is sent as the score `user_feedback` (`Tracer.score_feedback`, fixed `score_id` `feedback-<message id>` so re-rating overwrites). A reaper-written `failed` message has no trace id. **Verified against live Langfuse (2026-11-21):** a score sent twice for one trace id (+1, then -1) ends as ONE `user_feedback` score with value -1 and id `feedback-<message id>`, read back with `client.api.scores.get_many(trace_id=...)` (SDK 5 has no `api.trace.get`). The trace itself comes from the run's callback handler, checked with the in-memory exporter
- Threat IDs `LLM-T01…T20` (T19 retired with schedules) are defined in `docs/02_outputs/10_llm_threat_model.md`; red-team cases reference them
